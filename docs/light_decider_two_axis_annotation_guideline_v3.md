# light_decider 两轴标注细则 v3

**用途：** 在 v2 基础上约束后续标注与策略实现。v2 保持为历史版本；冻结的 24 条人工金标也保持不变。本文件新增的边界规则不得反向改写旧标签。

## 动作与判定顺序

先判断用户是否在请求执行代码/仓库工作；纯提问、比较或解释请求走 `decide`，不进入两轴。对执行类请求，先标“是否缺失关键规格”和“是否存在公认安全默认”，再按规则推导动作：

- 规格足够，且不依赖项目约定：`codex`。
- 缺少规格，但存在可逆、不会实质改变数据结果或业务语义的惯例：`codex+declare_default`。交接必须写出具体默认及理由；声明前检查直接冲突的现有约定，发现冲突时转 `codex+check_first`。
- 请求基于已有系统、迁移或延续现有行为：`codex+check_first`。交接必须列出检查位置；查不到一致约定或发现冲突时停止并转 `clarify`。
- 缺少关键规格且没有安全默认：`clarify`。

项目约定只适用于可在当前仓库中查证的实现细节。只有请求明确指向现有实现、当前系统、迁移或旧版流程/系统/API/服务时才走 `check_first`；业务数据中的“旧版本”（例如合同历史版本）本身不表示要沿用旧系统约定。不能用“先看看仓库”代替用户决定新业务语义。

## 关键选择由用户保留

以下判据按原文执行：

> 用户在请求里把某个关键选择**明确写成问句或二选一**的，视为用户保留决定权 → clarify，哪怕存在可逆的安全默认；用户根本没提及、且有可逆惯例可循的，才走 codex+declare_default。

该规则适用于明确要求实现/修改的请求，不把纯知识问答或方案比较误当成实现任务。冻结样本 `blind-015` 的标签仍为 `codex+declare_default`；按本规则，新策略会将其输出为 `clarify`，作为已知分歧单独验收，不能回改金标。

## 高危域与 override

高危域标记为 `payment`、`permission`、`locale_sensitive_parsing`、`deduplication`、`rate_limiting`。标记用于提高审查要求，不能单独推出动作。任何策略 override 都不得把带有这些标记的请求改向 `decide`；每次触发均记录改前动作、改后动作和规则名，若因高危规则拒绝应用，也记录被拦截的提议。

地区敏感解析覆盖金额、一般数字和日期/时间。高危域中用户明确授权采用默认时，交接仍须写明具体默认及理由；授权本身不会把没有安全依据的选择变成安全默认。

## 冻结样本对照

- `blind-005`：交接里要求写明采用样式是汇报要求，不是解释请求；按可逆样式惯例走 `codex+declare_default`。
- `blind-014`、`blind-020`：请求依赖现有生成器/队列约定，走 `codex+check_first`。
- `blind-023`：合同旧版本是待定义的业务保留策略，不是旧版系统；谁能看历史和保留期限缺失，走 `clarify`。
- `blind-018`：ETag 与 Last-Modified 的概念问题上下文自足，走 `decide`，不能因“它”触发缺失指代。
- `blind-021`：关系型与文档数据库的纯比较问题走 `decide`；“二选一”规则不适用于纯比较。
- `blind-015`：问句明确把删除与归档作为业务选择交给用户，按 v3 走 `clarify`；冻结标签维持 `codex+declare_default`，差异只用于已知分歧记录。
- `blind-003`、`blind-006`、`blind-010`、`blind-012`、`blind-016`、`blind-019`、`blind-023`：缺失的账户变更控制、提醒频率、限流窗口、地区格式、权限范围、并发冲突策略或合同历史访问/保留期限，均会改变结果，走 `clarify`。

## 回归与数据纪律

冻结金标仅用于策略回归与验收，不用于模型训练、调参或模型分数优化。每次修改策略都运行 `python scripts/run_frozen_gold_policy_regression.py`，记录完整动作翻转清单。`blind-015` 单独列为已知分歧；不得记为模型错误或标注错误。自动派发保持关闭。
